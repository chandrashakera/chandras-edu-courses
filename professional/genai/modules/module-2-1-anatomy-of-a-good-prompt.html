Anatomy of a Good Prompt

⏱ 12 min read 📝 Assignment inside

Welcome to Module 2. In Unit 1 you built a mental model of what GenAI is and where it fails. Now you start using it effectively.

This module teaches the single most important practical skill in this course: how to write a prompt that actually gets what you want. Most people who are disappointed with AI outputs are not using a bad tool — they are writing bad prompts. The model is only as good as the instructions you give it.

By the end of this module you will be able to break any task down into a structured prompt that produces consistent, high-quality output from any tool.

Why most prompts fail

Before learning what makes a good prompt, look at what makes a bad one.

A typical weak prompt
Write about AI in the Indian IT industry.

The bad prompt is not wrong — it is just empty. The model has no idea who you are, what level of detail you need, what format you want, or what context matters. So it produces a generic, mediocre response.

The good prompt gives the model everything it needs to produce exactly what you want on the first try.

The six components of a well-structured prompt

Every effective prompt is built from some combination of these six components. You do not need all six every time — but knowing each one lets you diagnose why a prompt is failing and fix it.

ComponentWhat it doesExample
RoleWho the model should act as"You are a data analyst at an Indian fintech startup."
TaskThe exact action you want"Summarise this sales report in 5 bullet points."
ContextBackground the model needs for your situation"This is for a client meeting tomorrow morning."
FormatLength, structure, layout"Under 100 words, as a bulleted list."
ExamplesA sample of the style or output you want"Match the tone of this example: ..."
ConstraintsWhat to avoid or limits to respect"Do not use technical jargon."

You rarely need all six at once. Start with Task, add Context and Format first — those three fix most weak prompts on their own.

Seeing all six in action

Here is the same task — asking for help preparing for a job interview — written as a weak prompt, then rebuilt using all six components.

Weak prompt
Help me prepare for a job interview.

What is wrong with this? The model does not know your background, the role you are applying for, what stage of interview preparation you are at, how much time you have, or what format of help you want. The output will be a generic list that could apply to anyone applying anywhere.

Rebuilt using all six components
Role: You are a senior technical interview coach who has prepared many freshers for Indian IT placements. Task: Build me a focused interview preparation plan. Context: I am a final-year B.Tech CSE student interviewing for a Software Engineer Trainee role at Infosys next week. My strengths are Java and DBMS; I am weak on system design basics. Format: A day-by-day plan for the next 5 days, as a table with columns Day, Topic, What to practise. Keep each row to one line. Examples: Match the tone of a mentor giving direct, practical advice — not generic motivational tips. Constraints: Keep the whole plan under 300 words. Do not include generic "be confident" advice.

The second prompt will produce a personalised, structured, immediately usable preparation plan — not a generic bullet list. The difference in output quality will be dramatic, and it took about 60 seconds longer to write.

The most common prompt mistakes — and how to fix them

  • Too vague — no clear task verb or outcome.
  • No audience — the model does not know who will read the output.
  • Missing context — no background on your actual situation.
  • No format — length, structure, and layout left undefined.

Tool-specific tips for Indian users

Different tools respond slightly differently to the same prompt structure. Here is what to know:

  • ChatGPT — responds well to numbered instructions; if it skips part of a long prompt, repeat that part as a short separate sentence at the end.
  • Claude — handles long, detailed prompts well; you can paste a whole document as context without it losing track of your instructions.
  • Gemini — say explicitly if you want it to search the web for current information, otherwise it may answer from training data alone.

The prompt improvement loop

Writing a good prompt is rarely a one-shot activity — it is an iterative loop. Here is the workflow that experienced prompt engineers use:

  1. Write — draft your prompt using as many of the six components as the task needs.
  2. Test — run it and read the output carefully, not just skim it.
  3. Diagnose — if something is missing or wrong, identify which component caused it.
  4. Refine — add or fix only that component, then test again.

Most prompts need 2–3 iterations to reach high quality. This is not a failure — it is the normal workflow. Each iteration teaches you something about what the model needs from you, and over time your first-draft prompts improve because you have internalised what "missing components" look like.

A practical template to start with

Until writing structured prompts feels natural, use this template for any task:

Six-component prompt template
Role: [who the model should act as] Task: [the exact action you want] Context: [background details relevant to this task] Format: [length, structure, layout] Examples: [an example of the style or output you want, if useful] Constraints: [anything to avoid or limits to respect]

You will not need this template forever — after 20–30 prompts, structuring this way becomes instinctive. But use it consciously for the next week and your output quality will improve immediately.

The three things to remember

  • A prompt is a specification, not a question — the more precisely you define role, task, context, format, examples, and constraints, the better the output. Vague prompts produce vague results.

  • The six components are your diagnostic toolkit — when a prompt gives a bad output, check which component is missing. Adding the missing piece is almost always faster than rewriting the prompt from scratch.

  • Refinement is the workflow, not a fallback — professional prompt engineers iterate 2–3 times per task. Accepting the first output and blaming the tool is the most common mistake beginners make.
