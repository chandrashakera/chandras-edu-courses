Common Prompt Mistakes

⏱ 12 min read 📝 Assignment inside

This is the final module of Module 2 — and the most practical one. You now have three modules of prompt engineering theory behind you. This module is about what goes wrong when you apply it, and how to fix it fast.

Every prompt that fails does so for a diagnosable reason. Once you learn to recognise the patterns, you will spend less time rewriting prompts from scratch and more time refining them precisely. The 10 mistakes in this module account for the vast majority of poor AI outputs that Indian students and IT professionals experience.

Mistake 1 — Too vague, no task verb

A vague prompt gives the model a topic but no clear instruction — no verb telling it what to actually do with that topic. The model has to guess whether you want an explanation, a summary, a list, or something else entirely.

Weak: "Cloud computing for my project."
Fixed
Explain cloud computing in 3 short paragraphs, suitable for a college project report introduction.

Why it works: "Explain... in 3 short paragraphs" gives the model a clear verb and a clear output shape — there is nothing left to guess.

Mistake 2 — No audience specified

Without knowing who will read the output, the model defaults to a generic, middle-of-the-road explanation — too simple for an expert, too technical for a beginner.

Weak: "Explain how Docker works."
Fixed
Explain how Docker works to a final-year CS student who knows programming but has never used containers before.

Why it works: naming the audience tells the model exactly which concepts to assume and which to explain from scratch.

Mistake 3 — Missing context

Context is the background information the model needs to give you an answer that fits your actual situation, not a generic one. Without it, you get advice that could apply to anyone.

Weak: "How do I ask my manager for a raise?"
Fixed
Context: I am a software engineer with 2 years at an Indian IT services company. I have taken on two extra projects this year and my last review was "exceeds expectations." Task: Draft what I should say when asking my manager for a raise.

Why it works: the context lets the model tailor the advice to your actual leverage, instead of giving generic negotiation tips.

Mistake 4 — No format specified

If you do not say how long or how the output should be structured, you might get three lines when you wanted a table, or 500 words when you wanted a one-line answer.

Weak: "Compare SQL and NoSQL databases."
Fixed
Compare SQL and NoSQL databases. Format as a table with columns: Feature, SQL, NoSQL. Keep it to 5 rows.

Why it works: specifying the format removes all ambiguity about length and layout, so you get a usable result on the first try.

Mistake 5 — Multiple tasks in one prompt

Stacking several unrelated requests into one prompt makes the model split its attention, and it often does each task shallowly or skips one entirely.

Weak: "Write my resume summary, suggest interview questions, and explain what a data lake is."
Fixed
Write a 2-line resume summary for a data analyst with 1 year of experience in SQL and Power BI.

Why it works: one focused task gets the model's full attention. Ask the other two questions as separate prompts.

Mistake 6 — Accepting the first output

The first response is a first draft, not a final answer. Most beginners stop here — which is exactly why one follow-up prompt is often the single highest-leverage thing you can do.

Weak: Accepting the first email draft and sending it as-is.
Fixed — a follow-up prompt
This is a good start. Now make it 30% shorter, more direct, and remove any sentence that does not add new information.

Why it works: a targeted follow-up prompt refines the output far faster than rewriting the whole prompt from scratch.

Mistake 7 — Not separating generation from verification

Asking the model to generate and silently trusting the result skips an easy safety check: asking the model to review its own work against specific criteria, in a separate step.

Weak: Generating a report summary and sharing it immediately.
Fixed — a verification pass
Check the summary above against the original data. Flag any number, date, or claim that is not directly supported by the source, and explain why.

Why it works: a model asked explicitly to verify catches its own mistakes far more often than one asked to simply "double-check."

Mistake 8 — Wrong technique for the task

Using zero-shot for a task that needs reasoning, or chain-of-thought for a simple task, wastes time either way — too shallow an answer in one case, an overlong one in the other.

Weak: Asking a multi-step budgeting problem with a plain zero-shot prompt, then accepting a number with no working shown.
Fixed
Work through this budget allocation step by step, showing your reasoning for each category, before giving the final numbers.

Why it works: matching chain-of-thought to a problem that actually needs multi-step reasoning produces a correct, checkable answer instead of a guess.

Mistake 9 — Generic domain language

Using vague, generic terms instead of the specific terminology of your field makes the model respond with surface-level, textbook answers instead of answers that fit your real context.

Weak: "Explain how our system handles errors."
Fixed
Explain how a typical microservices architecture handles error propagation between services, using terms like circuit breaker, retry policy, and dead-letter queue.

Why it works: naming the specific domain vocabulary signals the depth and precision you actually want, not a beginner-level explanation.

Mistake 10 — Outdated context in long conversations

In a long chat, the model keeps using earlier context even after your actual situation has changed — leading to answers based on facts that are no longer true.

Weak: Continuing a long chat about "the old API design" after switching to a new design, without telling the model anything changed.
Fixed
Ignore the API design discussed earlier in this chat — we have switched approaches. Here is the new design: [paste new details]. Answer my next questions based only on this.

Why it works: explicitly flagging what has changed stops the model from quietly blending old and new context into a confused answer.

The pre-submit prompt checklist

Print this. Stick it next to your monitor. Use it for the next two weeks until it becomes instinctive.

Before you submit any prompt, check:
  • Does it have a clear task verb? (explain, write, compare, summarise...)
  • Have I said who the output is for?
  • Have I given the context the model needs for my specific situation?
  • Have I specified the format and length?
  • Am I asking for one task, not several at once?
  • If this needs reasoning, have I asked for step-by-step thinking?

The three things to remember

  • Bad output is a specification problem, not an AI problem — every poor output has a diagnosable missing component. Use the symptom-to-fix diagnosis guide to identify it and the pre-submit checklist to prevent it.

  • First outputs are starting points — one targeted follow-up prompt improves output quality by 30–40%. Accepting first outputs is the most common mistake experienced users make.

  • Use a two-pass approach for anything important — generate first, then use a separate prompt to verify. Ask the model to check its own output against specific criteria. It catches its own mistakes well when asked explicitly.
