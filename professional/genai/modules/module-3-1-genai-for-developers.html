GenAI for Developers

⏱ 12 min read 📝 Assignment inside

Welcome to Module 3. You now have the prompt engineering skills from Module 2. This module is about applying those skills to your actual work — starting with the role most of you are entering or preparing for: software development.

This sub-module is not theoretical. Every technique here maps to a task you will meet in your first weeks at an Indian IT company — or in your current academic projects if you are still in college.

Why AI is now a baseline skill for developers

AI coding assistants are now a normal part of software work at large IT companies. Here is what the evidence actually says — both sides of it:

  • Scale: In its Q3 FY26 results call (January 2026), Infosys said its teams had generated over 28 million lines of code using AI.
  • Gains in an enterprise trial: In a study GitHub ran with Accenture developers (published 2024), the group using GitHub Copilot opened 8.69% more pull requests, had a 15% higher pull-request merge rate and 84% more successful builds. Developers accepted around 30% of Copilot's suggestions, which means they rejected most of them.
  • A warning from independent research: In a July 2025 randomised trial by METR, experienced open-source developers working on their own large projects took 19% longer with AI tools, even though they believed AI had made them faster.

The lesson: AI does not make every developer faster automatically. It helps most when you know which tasks to give it and you review its output quickly and carefully. That is exactly what this sub-module teaches.

Use case 1 — Code generation

For anything beyond a one-liner, describe the feature the way you would brief a colleague: stack, inputs, outputs, rules and edge cases. Use the six-component structure from Module 2.1.

Prompt 3.1A: Feature code generation
You are a senior Python developer. Context: I am building a REST API with FastAPI and SQLAlchemy for an online grocery store. Orders have fields: order_id (int), customer_id (int), items (list of {sku, qty, price_inr}), status ("PLACED", "PACKED", "SHIPPED", "DELIVERED", "CANCELLED"). Task: Write a POST endpoint /orders/{order_id}/cancel that cancels an order. Rules: - Only orders in PLACED or PACKED status can be cancelled; otherwise return HTTP 409 with a clear message. - Return 404 if the order does not exist. - Log every cancellation with order_id and timestamp. Output: the endpoint code, then a short list of the edge cases you handled.

For simpler functions — utility methods, data transformations, standard CRUD operations — GitHub Copilot inside VS Code is often the quickest option: it suggests code as you type, with no separate prompt needed. For complex features like the one above, a chat assistant (Claude, ChatGPT or Gemini) with a detailed prompt usually gives a more complete first draft. Always add your exact framework versions to the prompt.

Use case 2 — Debugging

Most debugging prompts fail because they paste only the error. The model needs four things: the error, the code, what you expected and what you already tried. Save this as your universal debugging template.

Prompt 3.1B: Universal debugging template
I am getting an error in my [language + framework + version] code. Error message (full, unedited): [paste] Relevant code: [paste the function and anything it calls] What I expected: [one or two lines] What actually happens: [one or two lines] What I have already tried: [list] Explain the most likely cause in plain language, give the fixed code, and tell me how to confirm the fix works. If there are several possible causes, rank them.

Never paste passwords, API keys, client data or proprietary code into a tool your company has not approved — replace them with placeholders first.

Use case 3 — Code review and improvement

A good review prompt tells the model what to look for and how to report it. Otherwise you get vague praise or a full rewrite you did not ask for.

Prompt 3.1C: Structured review prompt
Review the following [language] function as a strict senior reviewer. Check, in this order: 1. Bugs and incorrect logic 2. Unhandled edge cases (empty input, nulls, very large values) 3. Security issues (injection, unsafe input handling) 4. Performance problems 5. Readability and naming For each issue give: severity (High/Medium/Low), the line, why it matters, and a suggested fix. Do not rewrite the whole function unless I ask. [paste code]

Use case 4 — Writing tests

AI is useful for listing test cases you might miss, especially edge cases. Ask for the list first, check it, then ask for the test code.

Prompt 3.1D: Unit test generation
Here is a Java method that calculates GST-inclusive invoice totals: [paste method] Step 1: List the test cases you would write — normal cases, boundary values, invalid inputs — as a table with input, expected output and reason. Step 2: After the table, write JUnit 5 tests for every case. Use clear test names that describe the behaviour being tested.

Run the generated tests. A test that passes against buggy code is worse than no test, so read each assertion and confirm the expected value is actually correct.

Use case 5 — Writing documentation

Documentation is where AI saves time with the least risk, because you can check every line against the code in front of you.

Prompt 3.1E: Docstrings and README
For the Python module below: 1. Add Google-style docstrings to every public function: purpose, parameters with types, return value and exceptions raised. 2. Write a short README section with: what the module does, how to install dependencies, and one usage example. Do not change any code — documentation only. [paste module]

The AI-assisted development workflow

Here is how effective developers structure their AI usage — not using it for everything, but using it at the right points in the workflow:

  1. Plan yourself. Understand the requirement and decide the approach before you open any AI tool.
  2. Generate a first draft. Use a detailed prompt for features, or in-editor suggestions for boilerplate.
  3. Review every line. Read the code as if a junior colleague wrote it; use the structured review prompt for a second opinion.
  4. Test. Run existing tests, add new ones for the change, and check edge cases.
  5. Document. Update docstrings, comments and the README.
  6. Commit with your name on it. You are responsible for the code, whoever or whatever typed it.

What to never do with AI-generated code

  • Never commit code you have not read and understood
  • Never paste passwords, API keys, client data or confidential code into an unapproved AI tool
  • Never skip tests because "the AI wrote it"
  • Never add a library or package an AI suggests without checking that it exists, is maintained and has a compatible licence
  • Never trust AI-generated security code (authentication, encryption, input validation) without expert review
  • Never present AI-written code as entirely your own where disclosure is required

The three things to remember

  • AI generates a first draft, not a final product — even in a successful enterprise trial, developers rejected most suggestions. The skill is fast, accurate review — not blind acceptance. Read every line before committing.
  • Specificity is the difference between useful and generic code — include your exact stack versions, field names, business logic, error handling requirements, and output format in every code generation prompt. Vague prompts produce skeleton code you have to rewrite anyway.
  • Use the right tool for the right task — in-editor suggestions for boilerplate, a chat assistant with a detailed prompt for complex logic, reviews and documentation. No single tool is best at everything.

Your assignment

This assignment builds your prompt library for development work. Each task should take 15–20 minutes.

  • Code generation: Pick a function or feature you need to write for a current project, assignment, or practice problem. Write a detailed prompt using the six-component structure. Include your exact stack, requirements, and constraints. Test the output and note what you had to fix.
  • Debugging: Take a bug you are currently stuck on (or have been stuck on recently). Use the universal debugging template from this sub-module. Paste the error, code, and context. Note how long it would have taken you to find this manually versus with AI.
  • Code review: Take any function you have written in the past week — assignment, project, or practice code. Run it through the structured review prompt. Note what the model finds that you did not catch yourself.
  • Save all three prompts in your AI Learning Journal under "Module 3.1 — Developer Prompts." These form the start of your developer prompt library, which you will build out in Module 3.4.

After this assignment you will have concrete evidence of what AI can and cannot do for your development work — calibrated to your actual stack, not a generic tutorial example.
