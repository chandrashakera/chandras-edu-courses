Instruction Codes

⏱ 18 min read 📝 Quiz inside 📖 Mano, Ch. 5

Everything from here through the rest of this unit builds one concrete example — the Basic Computer, a small but complete machine used throughout this course to make "how a CPU actually executes an instruction" fully explicit. Its memory holds 4096 words of 16 bits each (a 12-bit address bus), and — following the stored-program idea — that same memory holds both data and the instructions that operate on it. What distinguishes an instruction from a data value is never the bit pattern itself; it's when the CPU is treating that memory word as an instruction versus as data.

The 16-Bit Instruction Word

Every Basic Computer instruction is a single 16-bit word split into three fields:

The 3-bit opcode alone can distinguish 8 instruction categories — 7 of them are memory-reference instructions, each combined with a 12-bit address (exactly enough to address all 4096 words). The 8th opcode pattern, 111, is special: instead of an address, its 12 remaining bits are individually decoded, one bit per operation — freeing up an entire second and third instruction category (register-reference and I/O) without spending any of the address space.

Direct vs. Indirect Addressing

Bit 15, I, controls how the address field is interpreted for memory-reference instructions:

IModeMeaning
0DirectThe address field is the effective address — AR ← IR(0–11) directly.
1IndirectThe address field points to a memory word that itself holds the effective address — AR ← M[IR(0–11)], one extra memory read before execution can begin.

Indirect addressing trades one extra memory access for a real capability: the effective address can now be changed at runtime — useful for anything that needs to compute an address rather than hardcode it (array indexing, pointer-following) without needing a wider address field.

Recognizing the Instruction Category

Opcode (IR bits 14–12) ≠ 111 → Memory-reference instruction (bits 11–0 = address) Opcode = 111, I = 0 → Register-reference instruction (bits 11–0 individually decoded) Opcode = 111, I = 1 → Input-Output instruction (bits 11–0 individually decoded)

Notice indirect addressing (I=1) only means something for a memory-reference instruction — for opcode 111, that same bit is instead reused as the switch between register-reference and I/O instructions. One bit, two completely different jobs, disambiguated entirely by which opcode it appears alongside.

Common Pitfalls

  • Treating I as "always meaning indirect addressing." It only has that meaning when the opcode is a genuine memory-reference opcode (000–110); for opcode 111 it selects between register-reference and I/O instructions instead.
  • Assuming the 12 bits of a register-reference instruction form a smaller address or a binary-coded sub-opcode. They don't — they're individually decoded, one flip-flop-worthy signal per bit, with (by design) only one bit ever set to 1 in a valid instruction.
  • Forgetting indirect addressing costs a real memory cycle. AR ← M[IR(0–11)] is an actual read from memory, taking a full clock period on top of whatever the instruction itself does — indirect instructions are strictly slower than direct ones.

Applications

  • Real instruction set architectures (x86, ARM, RISC-V) use exactly this same idea at a larger scale — a fixed opcode field selecting the operation, with special opcode values reserved for instruction families that don't need a memory address at all.
  • Indirect addressing is the direct ancestor of pointer dereferencing in every high-level language — "the value at the address stored in this variable" is precisely what I=1 computes in hardware.
  • The next topic, Computer Registers, introduces the actual hardware — IR, AR, PC, and the rest — that holds and decodes exactly the fields described here.
