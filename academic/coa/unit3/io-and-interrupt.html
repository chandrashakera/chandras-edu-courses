Input-Output and Interrupt

⏱ 22 min read 📝 Quiz inside 📖 Mano, Ch. 5

This closes out the Basic Computer: how it talks to the outside world, and how the outside world gets its attention back. Two completely separate mechanisms are at play here — device flags that report readiness, and an interrupt system that reacts to them.

The I/O Model

Computer Registers introduced INPR, OUTR, FGI, and FGO. The picture is a terminal: a keyboard feeding INPR, a printer fed by OUTR, each with its own ready flag that the device itself sets — completely independent of whatever the CPU happens to be doing:

  • FGI is set to 1 by the input device the instant a character lands in INPR — "there's something to read."
  • FGO is set to 1 by the output device once it's finished printing the last character — "I'm ready for another."

The CPU only ever clears these flags (after consuming/producing a character); it never sets them — that's entirely the device's job, running on its own timing.

RTL for the I/O Instructions

All six execute in a single state, T3 — opcode 111 instructions never need the indirect-address detour, since they don't use the address field at all (Computer Instructions):

p = D7 I T3   (common condition: opcode=111, I=1, timing T3)

p B11 (INP):  INPR ← input device,  FGI ← 0
p B10 (OUT):  output device ← OUTR,  FGO ← 0
p B9  (SKI):  if (FGI = 1) then (PC ← PC + 1)
p B8  (SKO):  if (FGO = 1) then (PC ← PC + 1)
p B7  (ION):  IEN ← 1
p B6  (IOF):  IEN ← 0

all:  SC ← 0

SKI and SKO are how a program without interrupts polls for I/O readiness — loop on SKI until it skips, then INP. That polling loop is exactly the problem interrupts exist to solve.

The Interrupt Cycle

IEN (interrupt enable) and R (interrupt flip-flop) are checked at the boundary between instructions — right where SC would normally reset to 0 for the next fetch:

When granted, the interrupt cycle saves the return address (the interrupted program's PC) at fixed memory location 0, then sets PC to 1. Location 1 is expected to hold a BUN to the actual interrupt-service routine — so execution resumes there, having stashed exactly where to come back to.

Common Pitfalls

  • Forgetting the ISR must execute ION before returning. The interrupt cycle clears IEN automatically (so a second interrupt can't corrupt the first one's return address) — if the service routine never re-enables it, no interrupt ever fires again.
  • Mixing up FGI/FGO with IEN/R. FGI/FGO are set by the devices themselves, asynchronously — they just report "ready." IEN/R are pure CPU-side control: IEN is a permission switch the programmer sets, R is set by the hardware once a check succeeds and cleared once the interrupt cycle runs.
  • Assuming "store return address at 0, jump via 1" is a universal rule. It's this specific machine's convention — real architectures use dedicated interrupt-vector tables, but the underlying idea (save where to resume, jump to a handler) is identical.

Applications

  • This fixed-address save-and-vector scheme is the direct, simplified ancestor of every real interrupt vector table — a fixed, known location the CPU always checks first when an interrupt fires.
  • FGI/FGO's device-sets / CPU-clears handshake is the same basic pattern behind status/ready flags in real device drivers today, just usually memory-mapped instead of dedicated flip-flops.
  • This is the last piece of the whole picture — Register Transfer Language's abstract micro-operations (start of this unit) have now become a complete, working CPU: registers, a bus, an ALU, a control unit, and I/O with interrupts.
