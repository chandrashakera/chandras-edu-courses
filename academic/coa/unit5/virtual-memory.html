Virtual Memory

⏱ 22 min read 📌 Supplementary — beyond the syllabus
In simple terms: virtual memory lets a program use more memory than the computer physically has. The program’s addresses are split into pages; only the pages in use sit in main memory, and the rest wait on disk until needed.

Why Virtual Memory

A program is written as if it had one large, continuous memory — its virtual (logical) address space. Main memory (the physical address space) is smaller and shared by many programs. Virtual memory keeps the active parts of each program in main memory and the rest on auxiliary memory (disk), and translates every virtual address to a physical one as the program runs. The programmer never sees the difference.

Paging and Address Translation

Virtual memory is divided into fixed-size pages; main memory into frames of the same size. A page table holds, for each page, the frame where it currently sits plus a valid (presence) bit. A virtual address splits into a page number p and an offset d; the page table turns p into a frame number f; the offset is copied unchanged.

Paging: the page number selects a page-table entry that supplies the frame number; the offset passes through unchanged.

Worked Example 1 — Translating an Address

Virtual address space 64K words (16-bit address), page size 1K words (10-bit offset)
→ page number = 16 − 10 = 6 bits (64 pages)
Physical memory 4K words (12-bit address) → 4 frames (2-bit frame number)

Virtual address 1A3F (hex) = 000110 1000111111
   page p = 000110 = 6      offset d = 1000111111 = 23F (hex) = 575
Page table: page 6 → frame 3 (binary 11)
Physical address = 11 1000111111 = E3F (hex)
Check: 3 × 1024 + 575 = 3647 = E3F (hex) ✓

Worked Example 2 — Page-Table Size

32-bit virtual address, 4 KB pages (12-bit offset)
→ 2(32−12) = 220 = 1,048,576 pages → one page-table entry each
4 bytes per entry → page table = 4 MB per program

This is why real systems use multi-level page tables and a TLB.

Page Faults

If the valid bit of the required page is 0, the page is not in main memory — a page fault. The operating system finds the page on disk, loads it into a free frame (or replaces a page if none is free), updates the page table, and restarts the instruction. A page fault costs milliseconds, so keeping the fault rate low matters.

The TLB (Translation Lookaside Buffer)

Reading the page table on every access would double memory traffic. A TLB is a small, fast associative memory that keeps the most recently used page-table entries.

Address translation with a TLB: a TLB hit skips the page-table read.

Worked Example 3 — Effective Access Time with a TLB

TLB lookup 20 ns, memory access 100 ns, TLB hit ratio 0.8
TLB hit : 20 + 100           = 120 ns
TLB miss: 20 + 100 + 100     = 220 ns   (page table read + data read)
EAT = 0.8 × 120 + 0.2 × 220  = 140 ns

Page Replacement

When a page fault occurs and every frame is full, one page must leave. The same policies as cache replacement apply — counted here as page faults:

PolicyReplaces
FIFOThe page loaded earliest
LRUThe page not used for the longest time
Optimal (OPT)The page whose next use is farthest away (benchmark only — needs the future)

Belady’s anomaly (FIFO only): with reference string 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5, FIFO gives 9 faults with 3 frames but 10 faults with 4 frames — more memory, more faults. LRU and OPT never behave this way.

Common Pitfalls

  • Changing the offset during translation. Only the page number is translated; the offset bits are copied as they are.
  • Mixing up page and frame. Pages belong to the virtual address space, frames to physical memory; they are the same size.
  • Assuming more frames always means fewer faults. True for LRU and OPT, but FIFO can show Belady’s anomaly.

Applications

  • Every modern OS (Windows, Linux, Android) uses paged virtual memory, so each program gets its own protected address space.
  • “Swap” space or a page file on disk is the backing store for pages not in RAM.
  • The TLB is part of every modern CPU’s memory-management unit (MMU).
