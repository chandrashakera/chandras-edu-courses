Decoders & Encoders

⏱ 20 min read 📝 Quiz inside 📖 Mano & Ciletti Ch. 4

Decoders and encoders are inverses of each other: a decoder turns a compact n-bit code into one active line out of 2ⁿ; an encoder turns one active line out of 2ⁿ back into a compact n-bit code.

Decoders

An n-to-2ⁿ decoder has n input lines and up to 2ⁿ output lines, and for every input combination, exactly one output is active (1) while all others stay 0. Each output is literally one minterm of the inputs.

ABD₀D₁D₂D₃
001000
010100
100010
110001
 
D₀ = A′B′   D₁ = A′B   D₂ = AB′   D₃ = AB

Most real decoder chips add an enable input E: every output AND gate gets a third input tied to E, so all outputs stay 0 whenever E=0, regardless of A and B. This is what makes decoders useful as chip-select logic — only the addressed chip's enable line goes active. Decoders Implement Any Boolean Function

Since every decoder output already is one minterm, implementing any Boolean function of n variables is just: feed the n variables into an n-to-2ⁿ decoder, then OR together whichever decoder outputs correspond to the function's minterms. This is the canonical-SOP idea from Unit 1, built directly in hardware with zero simplification needed.

Example: F(A,B) = Σm(1,2) — checking against the truth table above, m₁=A′B=D₁ and m₂=AB′=D₂, so F = D₁ + D₂: a single 2-input OR gate feeding off two of the decoder's outputs, no separate AND-gate array needed at all, since the decoder already built every minterm.

Encoders

An encoder does the reverse job: 2ⁿ input lines (only one active at a time) go in, and n output lines carrying that input's binary index come out. An octal-to-binary encoder (8 inputs D₀–D₇, one-hot; 3 outputs A₂A₁A₀) reads each output straight off which inputs include that bit position in their index:

A₀ = D₁ + D₃ + D₅ + D₇    (inputs whose index has bit 0 set)
A₁ = D₂ + D₃ + D₆ + D₇    (inputs whose index has bit 1 set)
A₂ = D₄ + D₅ + D₆ + D₇    (inputs whose index has bit 2 set)

Each output is simply an OR of the four input lines whose index has that bit position set — a plain encoder needs no AND gates or K-maps at all, just three 4-input OR gates. Here's the whole octal-to-binary encoder as a single block, every input and output drawn out individually:

Priority Encoder

A plain encoder assumes exactly one input is ever active — which real systems can't guarantee (two devices might request service in the same cycle). A priority encoder resolves this by always encoding the highest-indexed active input, ignoring lower-indexed ones even if they're also active:

D₃D₂D₁D₀A₁A₀V
0000XX0
0001001
001X011
01XX101
1XXX111

The X's are don't-cares (Unit 2 again) — once D₃ is known to be 1, D₂/D₁/D₀ genuinely don't matter for the output, since D₃ always wins regardless. V is a valid-output flag, 0 only when no input is active at all (needed because A₁=A₀=0 is otherwise ambiguous — does it mean "D₀ is active" or "nothing is active"?).

Common Pitfalls

  • Forgetting the enable input disables ALL outputs, not just one. E=0 forces every decoder output to 0 simultaneously — it doesn't select a "default" output, it silences the whole decoder.
  • Building a plain encoder when multiple inputs can be active at once. A plain encoder's outputs are undefined (or wrong) if more than one input is active simultaneously — that's exactly the situation a priority encoder is designed to handle correctly.
  • Ignoring the valid-output flag V. Without V, a priority encoder's all-zero output is ambiguous between "input D₀ is active" and "no input is active at all" — V is what disambiguates the two.

Applications

  • Memory address decoding is the textbook decoder application — a CPU's high-order address bits feed a decoder whose outputs become individual chip-select lines, exactly the enable-input pattern shown above.
  • Seven-segment display drivers are specialized decoders (BCD-to-seven-segment) that turn a 4-bit digit code into the right combination of active segments.
  • Interrupt controllers in a CPU use priority encoders to decide which of several simultaneous interrupt requests gets serviced first, exactly the "highest index wins" behavior shown above.
