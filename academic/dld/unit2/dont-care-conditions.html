Don't-Care Conditions

⏱ 18 min read 📝 Quiz inside

Every truth table so far has specified an output for every possible input combination. But some real circuits are only ever fed a limited subset of the theoretically-possible inputs — and for the input combinations that genuinely can't occur, the designer is free to assign whichever output value makes the resulting circuit simplest.

In simple terms: a don't-care is an input that never happens, so you may treat it as 1 or 0 — whichever makes the groups bigger.

What a Don't-Care Is

A don't-care condition is an input combination whose output value is unspecified — either because that input never actually occurs in the system, or because the application genuinely doesn't care what the output is when it does. Recall Unit 1's Binary Codes coverage: BCD only ever uses the bit patterns 0000 through 1001 — patterns 1010 through 1111 are invalid BCD digits that a correctly-functioning system will never actually produce. Any circuit built to process BCD digits can treat those six patterns as don't-cares.

Don't-cares are marked with an X (or sometimes d) in a truth table or K-map, distinct from both 0 and 1.

Using Don't-Cares in a K-Map

The rule is simple, and powerful: when forming a group, treat each X as either a 0 or a 1 — whichever produces a larger, more useful group — decided independently for each group. An X doesn't have to be included in any group at all if it doesn't help; it's genuinely optional, used only where it makes the result better.

Worked Example — F(A,B,C,D) = Σm(1,3,5,7,9) + d(10,11,12,13,14,15)

This function is 1 for the odd BCD digits 1, 3, 5, 7, 9, and 0 for the even BCD digits 0, 2, 4, 6, 8. The six invalid BCD patterns (10-15) are marked as don't-cares.

With don't-cares 11, 13, 15 taken as 1s, the two D = 1 columns form one group of eight: F = D.

Without don't-cares, m9 can only pair with m1 (the top and bottom rows are adjacent), giving F = A′D + B′C′D. With them, treat m11, m13 and m15 as 1s: the two D = 1 columns — m1, m3, m5, m7, m9 and d11, d13, d15 — form a single group of eight.

Group of 8 {m1, m3, m5, m7, m9, d11, d13, d15} (D = 1; A, B, C all vary): term = D

F = D      (d10, d12, d14 are not needed and are left as 0)

The entire function collapses to a single variable, F = D — a dramatically simpler circuit than what plain minterms alone would have produced, made possible entirely by choosing don't-care values strategically.

🚀 Verify it: F=D must equal 0 for every specified 0 (the even digits 0,2,4,6,8 — and indeed D=0 for all of them) and 1 for every specified 1 (the odd digits 1,3,5,7,9 — D=1 for all of them). The don't-care cells (10-15) are free to be whatever D happens to be there, which is exactly the point — since those inputs never occur, it doesn't matter.

Don't-Cares Apply to POS Too

The same freedom applies when minimizing a POS expression from the same K-map: each X can independently be treated as a 0 (joining a 0-group) or a 1 (excluded from consideration), whichever produces the largest, most useful 0-groups.

Common Pitfalls

  • Treating every don't-care the same way throughout the whole map. Different groups are free to use the same X cell differently — one group might treat a given X as a 1, while a different group (or no group at all) simply ignores it. There's no requirement to be globally consistent about a single X's "value."
  • Forgetting that don't-cares are optional, not mandatory. An X never needs to be circled if doing so doesn't help form a larger group — including an unhelpful X can even make the expression more complicated, not less.
  • Confusing "don't-care" with "unknown but real." A don't-care specifically means the input combination never occurs (or its output truly doesn't matter) — it's a deliberate design freedom, not a gap in the specification that needs to be filled in "correctly."

Applications

  • BCD-based circuits (seven-segment display decoders, BCD arithmetic units) are the textbook example — the six invalid BCD patterns are essentially always treated as don't-cares in real designs.
  • State machine design (covered later in this course) routinely produces don't-cares for unused binary state codes — if a machine only needs 5 of 8 possible states from 3 flip-flops, the 3 unused state codes become don't-cares in the next-state logic.
  • Any sensor or input system with a physically limited input range (e.g., a rotary switch with only 10 valid positions, but 4 bits of encoding that could represent 16) naturally produces don't-cares for the unreachable positions.
