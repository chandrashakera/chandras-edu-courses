State Diagrams & State Tables

⏱ 16 min read 📝 Quiz inside 📖 Mano & Ciletti Ch. 5

A state diagram and a state table describe exactly the same FSM — nothing is lost converting between them in either direction. The diagram is easier to read at a glance; the table is what you'll actually build excitation tables and K-maps from (next two topics), so being fluent in both directions matters.

State Table Format

Every state table has one row per state. What goes in the columns depends on the model:

Moore: Present State | Next State for each input value | Output (one per state) Mealy: Present State | Next State / Output pair, for each input value

That's the one structural difference to remember: a Moore table has output as its own separate column (one value per row, since output depends only on state); a Mealy table folds output into each next-state cell (one value per input per row, since output depends on the transition).

Diagram → Table: A Moore Example

Build a detector whose output goes to 1 once the input has shown a 1 followed later by a 0 — and stays 1 forever after, regardless of what comes next:

S0 = "haven't seen a 1 yet," S1 = "saw a 1, waiting for a 0," S2 = "saw 1-then-0 — done." S2's self-loop is labeled "0,1" because either input keeps it parked in S2 — once the pattern has been seen, nothing that follows changes the output. Reading each state's row mechanically off the diagram:

Present StateNext State (x=0)Next State (x=1)Output z
S0S0S10
S1S2S10
S2S2S21

The rule is entirely mechanical: for each state (row), follow the arrow leaving it for every possible input value, write down where that arrow lands (next-state column), and copy the state's own output into the output column since it's Moore.

Table → Diagram: A Mealy Example

Now go the other direction, starting from a table instead of a picture — this is the "detect two consecutive 1s" Mealy machine from the last topic, given here as a table first:

Present StateNext State/Output (x=0)Next State/Output (x=1)
S0S0 / 0S1 / 0
S1S0 / 0S1 / 1

To redraw this as a diagram: draw one circle per row (S0, S1). For each cell, draw an arrow from that row's state to the next-state named in the cell, labeled input/output. Row S0: the x=0 cell says "S0/0," so draw a self-loop on S0 labeled 0/0; the x=1 cell says "S1/0," so draw S0→S1 labeled 1/0. Row S1: the x=0 cell says "S0/0," so draw S1→S0 labeled 0/0; the x=1 cell says "S1/1," so draw a self-loop on S1 labeled 1/1. That's exactly the two-state diagram from the previous topic, rebuilt purely from the table with no guessing involved.

Common Pitfalls

  • Leaving a cell blank because "it's obvious." A state table row must specify the next state (and, for Mealy, the output) for every possible input value — an incomplete row means the FSM's behavior is undefined for that case, which is a real bug, not a shortcut.
  • Forgetting to draw self-loops. A transition from a state back to itself is just as real as any other arrow and must appear in the diagram — omitting it (as if "nothing happens" needs no arrow) is one of the most common state-diagram mistakes.
  • Putting a Mealy output in the wrong place when converting to a table. It belongs inside the same cell as the next-state it's paired with (e.g., "S1 / 0"), not in a separate column the way a Moore output would be.

Applications

  • HDL state machine code (Verilog/VHDL `case` statements inside an `always`/`process` block) is essentially a state table written in a programming-language syntax — the same present-state/next-state/output structure, just textual instead of tabular.
  • Formal verification tools that check an FSM for unreachable states or missing transitions work directly against the state table representation, which is exactly why every row needs to be complete.
  • The state table is the direct input to the next topic (state reduction) and the topic after that (deriving excitation equations) — everything from here through the end of this unit's design procedure builds on being able to read and write one correctly.
